## 6. ⛔ TWO TRAPS

### Trap 1 — `CoordinateOffsets::alloc_coordinate` looks reusable and is NOT

`schedule/ddc/v1.rs:2281` declares:

```rust
/// `sliceViewCoordinates_` where its `coordinates_` is non-empty, else `allocateCoordinates_`.
fn alloc_coordinate(&self, alloc: AllocId) -> Coordinate;
```

The capacity function's selector is a **different rule over the same two fields**
(`dsc2.cpp:3774-3778`):

```cpp
(row != -1 && myAllocNode->sliceViewCoordinates_.foldConstructed())
    ? myAllocNode->sliceViewCoordinates_
    : myAllocNode->allocateCoordinates_;
```

`row` has already been forced to `-1` for every component outside `{PTARF, PTIRF, PTXRF}`
(`:3768-3772`). Reusing `alloc_coordinate` silently picks the wrong coordinate. (Its only body
anywhere is a test double returning `Coordinate::default()` at `v1.rs:7975`.)

### Trap 2 — `FoldDim::cardinality_at` cannot reach the folds this body multiplies

`schedule/dsc2.rs:174` takes the **closed 3-variant** `FoldPosition` (`Core = 0`, `Corelet = 1`,
`RowSplit = 2`, `dsc2.rs:111-123`). The capacity walk multiplies in `ELEM_ARR_COORD` folds, which sit
at positions **≥ 2** — `dimCoord.getFoldDimSize(foldPos)` for `foldPos` in `0..getNumDims()`. Use
`folds().enumerate()`; the named accessor cannot express it. (This is inside the deferred
`useCoordinate` arm — so the trap is: do not reach for `cardinality_at` when you eventually port it.)
